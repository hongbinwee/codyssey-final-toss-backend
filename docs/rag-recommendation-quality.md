# 추천 품질 개선 구현

> 기록 시점: 커밋·푸시 전 구현 정리. 이후 사용자가 GitHub 푸시를 요청했으며,
> 실제 커밋·원격 공유 상태는 Git 기록으로 확인한다. 운영 배포·색인 전환 여부와 구분한다.

## 추가 수정: 상품 관련성 검사 v2

사용자가 제시한 “세제 사고 싶어 → 이어폰·클립·키링 추천” 사례를 기준으로
기존 검색 흐름의 상품 관련성 검사를 보강했다. 버전은 `product-hybrid-v2`,
레지스트리는 `product-types-v2`다.

- `detergent`는 세탁·주방·식기세척기용 세제의 상위 상품군이다.
  용도를 아직 말하지 않았어도 해당 상품군 안에서 검색한다.
- `protein_food`는 단백질 보충 식품의 상위 상품군이다. 분말/쉐이크·음료·스낵 등의
  하위 유형을 포함하고, `food` 범위를 요구해 단백질 헤어 제품과 구분한다.
- 유형의 `parents`, `categories`는 JSON 설정으로 확장한다. 존재하지 않는 부모,
  순환 관계, 서로 충돌하는 카테고리 범위는 설정 오류로 처리한다.
- 원문 `original_question`, 검색어 `query`, 명시적 `product_type`를 함께 확인한다.
  원문과 검색어가 서로 다른 상품군을 가리키면 `low_relevance`를 반환한다.
  검색어에 유형이 빠졌다면 원문의 유형을 사용한다. 같은 상품군 안의 구체적인 유형을
  임의로 상위 유형으로 넓히지 않는다.
- 검색 전 카탈로그 검사와 검색 후 payload 검사 모두 통과한 상품만 순위 계산에 넣는다.
  가격·리뷰·벡터 순위가 높아도 이 검사를 우회할 수 없다.
- 응답의 `ranking.relevance_qualified`, `requested_product_type`과
  `search_context.accepted_product_types`, `relevance_rejected_products`로
  검사 적용 여부와 제외 수를 전달한다. 이는 검수된 정확도나 관련성 확률이 아니다.
- 원문과 카테고리 범위가 충돌하면 `category_type_mismatch`를 사유로 빈 결과를 반환한다.

이 변경은 이 Backend 저장소의 Python RAG 서비스에 적용한 소스 수정이다.
별도 저장소의 Shopping Brain `src/brain/local-rag.ts`를 직접 변경하지 않았으며,
화면 서버가 로컬 RAG를 선택했다면 이 변경은 자동으로 사용되지 않는다.
Brain팀은 수정된 검색 서비스로 연결하거나 같은 상품 유형 검사를 로컬 검색에도 적용해야 한다.
로그인이 필요한 화면 서버의 실제 실행 모드는 확인하지 못했다.

문법 컴파일·모듈 로딩과 정적 검토만 진행했다. 자동 테스트, 실제 검색 재평가,
운영 컨테이너 교체, 재임베딩, 데이터 수정은 이 추가 수정에서 실행하지 않았다.
기존 PDF는 v1 작성 당시의 스냅샷이며 이 추가 변경은 본 문서가 최신 기록이다.

## 범위와 상태

2026-10-19 사용자가 승인한 개선 방향을 기존 RAG 서비스에 구현했다.
개발 저장소는 `hongbinwee/codyssey-final-toss-backend`, 브랜치는
`feature/rag-recommendation-quality`다. 시작점인 원격 main에는 README만 있어,
현재 실행 중인 서비스의 코드를 이 브랜치에 가져와 개선했다.

이 문서와 코드는 **로컬 구현 상태**다. 운영 컨테이너 교체, 원본/색인 수정,
재임베딩, 커밋, GitHub 푸시, main 병합을 수행한 기록이 아니다.
별도 테스트 요청 없이 자동 테스트나 품질 평가를 실행하지 않았다.
문법 컴파일과 정적 검토만으로 추천 품질 향상을 확정할 수 없다.

## 연결과 역할

```text
질문 → Shopping Brain: category, product_type, 예산 구조화
     → RAG: 허용된 profile의 카탈로그에서 상품 정체성 확인
     → Commerce reader: 같은 옵션의 가격·재고로 후보 자격 확인
     → RAG: BM25/벡터 → 상품 단위 결합·재정렬 → 리뷰 근거
     → Shopping Brain/LLM: 미검증 조건과 출처를 유지해 응답
```

- 모든 PostgreSQL 연결은 **5432**만 허용한다.
- RAG: `5432/toss_rag`, `rag` 스키마.
- 상품·옵션: `5432/toss`, 서버의 `COMMERCE_SCHEMA_MAP`에 설정된 스키마.
- 데이터 원본과 기존 `test_items2` 임베딩을 재사용하며 상품·리뷰 ID를 변경하지 않는다.
- Shopping Brain 코드는 이 저장소에 없으므로 카테고리 분류기나 LLM 응답 생성기를 추가하지 않았다.
- Brain은 카테고리/상품 유형을 판단한다. RAG의 키워드 유형 추론은 기존 호출 호환용이다.

## 요청 계약

기존 `POST /v1/rag/search` 경로를 유지한다. 다음 필드를 추가했다.

| 필드 | 기본값/의미 |
|---|---|
| `profile` | 생략 시 서버 `RAG_DEFAULT_PROFILE`; `RAG_ALLOWED_PROFILES` 밖의 값은 422 |
| `product_type` | 선택적. Brain이 판정한 정규 유형 ID 또는 유형명 |
| `filters.in_stock` | 생략 시 서버 정책(기본 true); 명시적인 false는 품절 포함 탐색 |

```json
{
  "request_id": "backpack-001",
  "original_question": "통학용으로 5만원 이하 백팩을 추천해줘",
  "query": "통학용 백팩",
  "category": "fashion",
  "profile": "test_items2",
  "product_type": "backpack",
  "filters": {"price_max": 50000, "currency": "KRW", "in_stock": true},
  "top_k": 5
}
```

서버 샘플 설정은 기본 프로필을 `test_items2`로 지정한다. 기존 beauty 전용 데이터
고정 조건을 검색/healthz에서 제거했다. `/v1/catalog/test-items`와 그 리뷰 경로는
기존 `all_products` 데이터에 독립적으로 고정해 유지한다. 해당 레거시 목록은
새 `test_items2` 목록을 뜻하지 않는다.

기존 응답 필드에 다음 정보를 추가한다. 엄격한 응답 모델을 사용하는 팀은 새 필드를
허용하거나 응답 모델에 추가해야 한다. 요청의 `max_price` 같은 최상위 필드 대신
기존 계약의 `filters.price_max`를 사용한다.

- `profile_name`: 실제 선택한 프로필.
- `search_context`: 유형 판정 경로, 규칙 버전, 후보 수, 빈 결과 사유.
- `items[].commerce`: 선택한 `variant_id`, 해당 옵션의 가격·재고, 조회 시각, 원본 스키마.
- `items[].ranking`: 상품명 일치와 어휘 커버리지. 관련성 확률을 뜻하지 않는다.
- `evidence[].review_bm25_rank`, `review_vector_rank`: 리뷰 전용 검색 순위.

## 검색과 정렬

1. 현재 run의 상품 유형을 확인해 부적합한 유형을 검색 전에 제외한다.
2. 가격·재고는 해당 유형의 전체 후보에 적용한다. 초기 검색 상위권 밖의 저렴한 상품도
   검색 기회를 얻도록 자격을 먼저 확인한다.
3. 각 채널은 서로 다른 상품을 기본 50개까지 확보한다. 상품당 최대 3청크를 보관하며,
   초기 창에 같은 상품이 몰리면 최대 2,000청크까지 창을 넓힌다. 이 상한 때문에 항상
   50개를 보장하지는 않는다.
4. 상품별 채널 순위로 RRF를 계산해 리뷰/청크 수가 많은 상품의 중복을 줄인다.
5. 상품명과 상품 정체성에 대한 어휘 일치 → 상품 RRF → 안정적인 ID 순으로 정렬한다.
   현재 재정렬은 결정적 규칙이며 별도 cross-encoder 모델을 도입한 것은 아니다.
6. 리뷰 의도가 있으면 리뷰 전용 두 채널의 후보도 결합하고 근거로 사용할 수 있다.
7. 유형이 없거나 불명확한 질문에는 카탈로그 상품명·브랜드·유형과의 어휘 연결을 요구한다.
   여러 유형이 모호하게 섞이면 `low_relevance`와 빈 배열을 반환해 Brain이 재질문하게 한다.

`src/toss_ads/rag/product_types.json`은 상품 ID와 독립적인 편집 가능한 유형/별칭 목록이다.
새로운 카테고리나 유형은 레지스트리와 상품의 검수된 `features.canonical_product_type`으로
확장한다. 레지스트리는 프로세스에서 캐시되므로 수정 후 서비스를 재시작해야 한다.
검수된 정규 유형이 있으면 상품명 추론보다 우선한다. 그렇지 않으면 사은품 구간을 뺀
주상품명을 우선하고, 충돌하는 유형을 넓은 원본 분류로 덮어쓰지 않는다.

이 규칙은 의미 이해 모델의 대체물이 아니다. 오탈자, 별칭 누락, 긴 사용 목적 질문,
묶음 상품, 원본 오분류에서는 누락/오판이 가능하다. 검수된 정규 유형과 Brain의
명시적 `product_type` 전달을 권장한다.

## 가격·재고와 조건

`CommerceStore`는 SELECT 전용 쿼리를 REPEATABLE READ / READ ONLY 트랜잭션에서 실행한다.
5초 쿼리 제한을 적용하며 스키마 식별자는 서버 설정에서만 가져온다.

- **같은 옵션**에서 예산과 재고를 함께 만족해야 한다.
- 조건을 만족하는 옵션 중 최저가와 ID 순으로 하나를 선택한다.
- 표시 가격도 선택한 옵션 가격으로 바꿔 품절 최저가를 표시하지 않는다.
- 조회 불가/권한 부족/필수 Commerce 설정 누락 시, 검증되지 않은 상품으로 대체하지 않는다.
- KRW만 지원한다. 환율 변환 없이 다른 통화 요청은 `unsupported_currency`(422)다.
- `test_items2`의 CANDIDATE/관측 가격을 실시간 외부 판매가로 보장하지 않는다.
  응답에 데이터 상태·가격 근거와 시뮬레이션 표시를 유지한다.
- 재고는 조회 시점의 값이다. 주문 시에는 Commerce가 다시 확인해야 한다.
- `required_conditions`와 `preferences`의 임의 문장을 사실로 검증하지 않는다.
  `unverified_conditions`를 LLM과 UI에 전달하고 충족했다고 단정하지 않아야 한다.

실제 구매 전 확인할 수 없는 복잡한 필수 조건은 Brain이 추가 질문하거나 해당 상품의
추천을 보류해야 한다. API가 `ok`여도 이 배열이 비어 있지 않으면 모든 조건 충족을
뜻하지 않는다.

## 리뷰와 청킹

- 기존 색인에서도 관리용 필드와 의미 없는 짧은 리뷰 조각은 검색 근거에서 제외한다.
- 동일 리뷰의 여러 조각이 근거 슬롯을 독점하지 않게 하고 실제 리뷰를 합성 리뷰보다 우선한다.
- 리뷰 의도가 있으면 사용할 수 있는 리뷰 근거를 최소 하나 포함한다. 리뷰가 검색되지
  않았다면 만들어내지 않는다. 합성 근거의 `source_kind`를 그대로 전달한다.
- 청커 버전은 `source-evidence-token-v3`다. 관리용 ID·수집/평가 통계는 임베딩 본문에서
  제외하고, 짧은 마지막 조각은 합치거나 앞 조각과 경계를 재배분한다.
- 원본 문장을 요약/변경하지 않으며 토큰 상한과 원문 offset을 유지한다.
- **v3 코드 작성만으로 기존 114,106개 청크가 바뀌지 않는다.** v3를 실제 색인에 적용하려면
  별도 run을 생성·검증한 뒤 프로필을 전환해야 한다. 기존 원본과 run은 보존한다.

## 배포 준비

1. `deploy/product-rag-runtime.env.example`을 로컬 비밀 파일로 복사하고 실제 계정을 설정한다.
2. `COMMERCE_DATABASE_URL`의 계정에 `toss` 접속 및 사용할 스키마의 USAGE,
   `products`, `product_variants` SELECT 권한이 있는지 확인한다. 권한 변경은 별도 작업이다.
3. 새 DB/포트 생성 없이 이미지에 이 브랜치의 `src`를 포함한다.
4. 설정을 적용한 뒤 기존 서비스 주소/포트에서 교체한다. 현재 작업은 이를 실행하지 않았다.
5. `/healthz`에서 프로필·데이터 버전·카테고리·Commerce 설정을 확인한다.
   healthz의 `commerce_configured`는 설정 유무이고 모든 스키마 권한의 검증 결과가 아니다.

현재 5432에는 프로필 테이블이 이미 있으므로 초기화 SQL을 다시 실행할 필요가 없다.
`deploy/product-rag.sql`은 프로필별 활성 run을 지원하는 신규 설치/레거시 전환용이며
이번 작업에서 실행하지 않았다.

## 품질 평가 기준

기존 24개 자연어 질문의 참고 수치는 Hit@1 58.3%, Hit@5 91.7%다. 자동 생성한 상품군
정답을 사용한 탐색적 평가였으며 공식 정확도나 독립적인 holdout으로 취급하지 않는다.

추후 요청 시 기존 질문은 회귀 확인용으로 재사용하고, 별도로 사람이 검수한 고정 정답과
독립 holdout을 준비해 BM25 단독/벡터 단독/기존 Hybrid/새 Hybrid를 비교한다.
상품 유형, OOD, 가격·재고, 리뷰 provenance, HTTP/Brain E2E, p95 지연을 함께 측정한다.
동일 평가셋 결과를 확인하기 전에는 개선 폭이나 목표 달성을 주장하지 않는다.
