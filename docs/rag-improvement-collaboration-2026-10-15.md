# RAG 검색 근거와 Agent 연동 개선 제안

**기준일:** 2026-10-15  
**상태:** RAG/Backend·AI Agent·데이터/API 담당자 공동 검토 초안  
**목적:** 청크 예시를 더 늘리기보다, 검색 결과가 Agent의 근거 있는 답변으로 이어지는지 확인하고 다음 협업 작업과 승인 지점을 정한다.

## 제안 요약

먼저 검색 상태와 상품별 추천 조건의 의미, 평가 라벨을 공동으로 정한다. 이 결정은 계약·평가 작업에 필요하지만 토큰 표본 재생성을 막지는 않으므로 두 작업은 병행할 수 있다.

1. 기존 30개 상품·119개 리뷰 표본을 토큰 기준 청커로 다시 만들고 실제 입력 길이와 원문 복원을 확인한다.
2. tuning 라벨을 합의하고 검색 실패를 분석한다. 검색 설정을 고정하고 기대 원문 근거가 여전히 유효한지 확인한 뒤 별도 holdout을 실행한다.
3. Agent가 사용할 상품 단위 응답 계약과 정상·가격 누락·근거 없음 예시를 확정한다. 계약 검토는 표본 재생성과 병행할 수 있다.
4. 계약 승인을 받은 뒤 Agent와 함께 가격 미확인, 리뷰 수 혼동, 일부 리뷰의 과잉 일반화, 리뷰 본문 속 지시문을 검증한다.

품질 기준과 연동 계약이 합의되기 전에는 전체 데이터 일괄 임베딩을 시작하지 않는다. 재랭커와 복수 모델 비교도 우선순위에서 제외한다.

## 현재 확인된 상태

| 영역 | 현재 근거 | 아직 확인할 점 |
|---|---|---|
| 청킹 파일럿 | 기존 표본 30개 상품·119개 리뷰에서 521개 청크를 만들었다. 이 파일럿은 `pilot-char-v1`, 최대 800자 기준이다. | 이 결과물은 새 토큰 청커로 다시 만든 것이 아니다. |
| 토큰 기준 청커 | Backend 청커는 FastEmbed의 동일 토크나이저로 입력을 세고 기본 상한을 96토큰으로 둔다. Backend 색인 경로가 이 청커를 사용한다. 별도의 fixture 색인에는 10개 상품·10개 리뷰, 32개 청크가 사용됐다. | 30개·119개 파일럿의 토큰 기준 산출물, 초과 여부와 원문 복원 결과를 한 보고서로 남겨야 한다. |
| 실제 검색 | tuning 12문항을 실행했다. 상품 적중은 12/12, 기대 출처 적중은 11/12, 잘못된 근거는 0건이다. RAG-017은 상품을 찾았지만 기대한 리뷰 청크가 상품당 근거 3개 제한에서 빠졌다. | 이 결과는 전체 통과가 아니다. tuning 라벨은 팀 검토 대기이고, holdout 8문항은 실행하지 않았다. |
| 저관련성 판정 | `RAG_MIN_RRF_SCORE` 기본값은 미설정이다. 설정돼도 현재 코드는 모든 반환 후보가 임계값 미만일 때만 `low_relevance`를 반환하고 결과 상품을 비운다. 한 상품이라도 통과하면 현재는 나머지 후보도 함께 `ok`로 반환한다. | 이 값은 검색 관련성 정책의 후보일 뿐 정답 확률이나 예산·평점 조건 판정이 아니다. 관련 문서 누락과 무관한 문서 통과를 함께 평가해야 한다. |
| Agent 계약 | 상품 단위 응답 스키마와 정상·자료 없음·저관련성·오류 예시가 있다. 현재 구현은 `top_k` 상한의 서로 다른 상품을 반환하고 상품별 최대 3개 근거를 붙인다. | 적합한 후보가 적을 때 결과를 무관한 상품으로 채우지 않는 의미를 명시해야 한다. 계약은 제안 상태이며 가격 누락 예시와 Agent 답변 검증이 남았다. |
| 조건 전달 | 현재 `unverified_conditions`는 요청에서 온 전역 문자열 목록이다. 가격 범위는 하드 필터로 적용되지 않는다. | 현재 응답은 조건을 상품별로 평가하지 않는다. 상품 ID와 조건을 연결하는 계약 및 구현이 필요하다. |
| Agent 안전·근거 사용 | RAG는 검색 결과를 제공한다. | Agent가 미확인 조건을 어떻게 답변에 반영하는지, 리뷰 속 지시문을 무시하는지 검증하지 않았다. |

현재 청킹 파일럿 보고서의 `full_index_ready`는 `false`다. 파일럿 결과와 검색 평가용 10개 상품 fixture 색인은 서로 다른 산출물로 구분한다.

## 작업안과 완료 기준

### 1. 같은 표본을 토큰 기준으로 재생성

**담당:** RAG/Backend  
**협의:** 데이터/API 담당자

- 동일한 30개 상품과 그에 연결된 리뷰를 새 토큰 청커로 처리한다. 현재 96토큰은 조정 가능한 기본 설정이며 그 숫자 자체가 합격 기준은 아니다.
- 제한 검사는 원문 근거만이 아니라 상품명·리뷰 제목·필드 문맥을 포함한 최종 `embedding_text`에 대해 수행한다. 특수 토큰을 포함해 실제 임베딩 경로에 전달되는 입력 길이를 검사하고, 사전 검사와 실제 임베딩 경로의 길이 제한·잘림 설정이 일치하는지 확인한다.
- 청커의 토큰 예산과 실제 임베딩 경로의 입력 한도를 각각 기록한다. 문맥과 특수 토큰을 포함한 최종 입력이 청커의 예산 및 실제 입력 한도 안에 들어오고, 임베딩 과정에서 추가로 잘리지 않는지 확인한다.
- 각 청크의 `source_field`, `start_offset`, `end_offset`, `evidence_text`가 원본을 가리키는지 검사한다.
- 필드별 청크를 원래 순서로 이어 붙였을 때 전체 대상 원문과 일치하고, 누락·겹침·토큰 초과가 0건인지 기록한다.
- 긴 상품명이 문맥 예산을 차지해도 원본 제목과 출처는 보존한다. 검색용 문맥을 줄이는 경우 잘린 문맥 길이와 정책을 보고서에 기록한다.

**완료 산출물:** 새 `report.json`, `chunks.jsonl`, `source_samples.jsonl`. 보고서에는 청커 버전, 토크나이저/모델, 실제 임베딩 길이 제한과 잘림 설정, 전체 청크 최대 입력 길이, 잘림 검사 결과, 원문 복원 결과, 미검증 항목을 적는다.

### 2. 실제 검색 평가를 tuning과 holdout으로 분리

**담당:** RAG/검색  
**공동 검토:** AI Agent·기획·데이터 담당자

현재 tuning 사례를 기준으로 아래 질문 유형을 포함한다.

- 상품명·모델명을 직접 지정한 검색
- 기능이나 사용 목적을 설명한 검색
- 한국어 질문으로 영어 상품 정보와 리뷰를 찾는 검색
- 리뷰에서 문제·불편을 찾는 검색
- 표본에 답이 없거나 요청 조건을 확인할 근거가 없는 검색

각 사례에 기대 상품 ID, 기대 출처 ID와 필드, 기대 원문 구간, 기대 상태를 팀이 먼저 검토한다. 기대 근거는 chunk ID가 아니라 원본 출처·필드·구간으로 기록한다. 청커 변경 후에는 기대 구간이 현재 원본에서 여전히 유효한지 확인하고, 반환된 청크의 원문 구간이 그 근거를 실제로 포함하는지 평가한다.

RRF 임계값은 관련성 판정의 후보 정책으로 평가한다. RRF 점수는 여러 검색 순위를 합친 값이며 정답 확률이 아니다. 결합하는 검색 목록 수와 순위, RRF 상수에 따라 값의 크기가 달라질 수 있으므로, 관련 문서를 잘못 제외하는 경우와 무관한 문서를 통과시키는 경우를 함께 확인한다. 검색 구성이나 평가 표본이 바뀌면 임계값을 재검증한다. [Microsoft의 RRF 설명](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)도 결합되는 검색 목록 수에 따라 점수 상한이 달라짐을 설명한다.

평가 근거가 부족하면 `RAG_MIN_RRF_SCORE`를 설정하지 않고 `low_relevance` 판정을 확정하지 않는다. 현재 구현에서 임계값이 미설정이면 후보가 있는 응답은 `ok`가 되므로, 이 상태를 저관련성 평가가 끝난 것으로 설명하지 않는다.

holdout 전에 아래 설정을 한 실행 manifest로 기록하고 고정한다.

- 평가 데이터 버전과 실제 색인 실행 ID
- 청커 버전과 최대 토큰 설정
- 임베딩 모델·토크나이저 버전과 실제 입력 길이/잘림 설정
- BM25·벡터 후보 깊이, 결합 방식과 RRF 상수
- 저관련성 임계값 또는 미설정 상태
- 상품 순위 및 상품별 근거 선택 방식, 근거 최대 개수

**순서:** 승인된 기대 원문 라벨과 합격 기준 → tuning 12문항으로 근거 선택 및 후보 정책 조정 → 위 manifest 고정 → 기대 원문 라벨 재검토 → holdout 8문항 별도 실행. holdout 결과 때문에 검색 설정을 바꾸면 변경 사실을 기록하고 새 holdout을 준비한다. 결과는 “검토한 tuning·holdout 표본에서”라고 표현하고 전체 데이터 품질로 확대하지 않는다.

RAG-017의 누락은 현재 확인된 개선 대상이다. 질의가 리뷰를 찾는지 상품 정보를 찾는지 전달하는 범위 힌트가 필요한지 Agent와 합의하고, 적용한다면 리뷰 질문·상품 속성 질문 모두로 회귀 평가한다. 근거 3개 제한이나 상품명 청크를 일괄 제거하는 변경은 전체 사례 결과를 비교한 뒤 결정한다.

**완료 산출물:** 승인된 평가 세트, 실행 manifest, tuning 및 holdout 보고서, 실패 사례와 수정 이력. 관련성 라벨과 허용 가능한 누락률은 팀이 실행 전에 합의한다.

### 3. 상품 단위 RAG → Agent 계약 확정

**담당:** RAG/Backend·AI Agent 공동

현재 구현을 바탕으로 아래 의미를 계약에 명시하고 Agent가 수용할 수 있는지 확인한다.

- `top_k`는 반환할 **서로 다른 상품의 최대 수**다. 청크 수가 아니다. 적합한 후보가 부족하면 적은 수를 반환하며 무관한 상품으로 채우지 않는다.
- 각 상품은 같은 상품에서 나온 근거를 `evidence` 배열에 묶는다. 각 근거에 `chunk_id`, `source_id`, `source_field`, 데이터 버전, 원문 근거와 오프셋을 유지한다.
- 가격·평점 등 상품 원본 메타데이터와 검색된 리뷰 근거는 별도 필드로 전달한다.
- 관련성 기준 통과·미달 상품이 함께 검색되는 경우, 미달 상품을 제외할지 상품별 관련성 판정과 함께 전달할지 합의한다. 최상위 `ok`를 모든 반환 상품의 관련성 통과로 해석하지 않으며, 혼합 후보 사례를 평가에 포함한다.
- 최상위 `status`는 검색 상태만 표현한다. `low_relevance`는 검증된 검색 관련성 정책의 기준 미달을 뜻한다. 예산 초과, 가격 미상, 평점·리뷰 수 조건의 불충족 또는 확인 불가는 `low_relevance`로 처리하지 않는다. `ok`도 추천 조건을 충족했다는 뜻이 아니다.
- 추천 조건 판단은 상품별 검색 상태와 분리한다. 가격 초과는 확인된 불충족, 가격/통화 부재는 확인 불가로 구분한다. `unverified_conditions` 항목은 최소한 `product_id`와 해당 조건을 식별해야 한다. `unmet`와 `unknown`을 표현할 위치·형식은 계약 검토에서 정한다.
- 현재 v0.2와 Backend 코드는 최상위 `unverified_conditions: string[]`로 요청 조건을 전역 전달하며 상품별 조건을 평가하지 않는다. 위 상품별 표현은 계약/구현 변경 제안이다. 기존 문자열만으로 조건이 어떤 상품에 해당하는지 추정하지 않는다.

계약 논의용 예시는 다음과 같다. 필드명은 합의 전 제안이며, 이 객체는 검색 응답의 최상위 `status`를 바꾸지 않는다.

```json
{
  "product_id": "9792284354",
  "condition": "price_max",
  "result": "unknown",
  "reason": "가격 통화를 확인할 수 없음"
}
```

알 수 없는 조건만 `unverified_conditions`에 둔다면, 확인된 조건 불충족은 상품별 조건 결과로 별도 전달한다. 어느 경우든 결과는 상품 ID와 요청 조건에 연결한다.

- 원본의 전체 평가/리뷰 수와 현재 검색 결과에서 반환한 리뷰 근거 수를 구분한다. `rating_number`의 원본 의미와 Agent 표시 문구는 데이터/API 담당자가 확인한다.
- 검색 점수는 확률로 표시하지 않는다. 미확인 조건을 충족한 사실처럼 변환하지 않는다.
- 실제 RAG 반환 필드인 JSON Pointer 형식의 `source_field`를 Agent가 처리할 수 있는지 확인한다.

먼저 아래 세 응답 JSON 예시를 확정한다.

1. 근거와 상품 메타데이터가 있는 정상 결과
2. 가격이 없거나 통화가 확인되지 않아 예산 충족 여부를 말할 수 없는 결과
3. 조건에 맞는 근거를 찾지 못한 결과

두 번째 예시는 `price`를 생략할지 `null`로 보낼지 팀이 선택하고, 상품 조건 결과와 검색 상태를 별도 위치에 보여준다. 세 번째 예시는 실제 후보가 없는 `no_results`와 검색 관련성 정책의 기준 미달인 `low_relevance`의 구분을 보여준다. 예산·평점·리뷰 수 조건의 미충족/확인 불가를 세 번째 예시의 `low_relevance`로 표시하지 않는다. `low_relevance`의 평가 근거가 부족하면 해당 판정을 계약상 확정하지 않는다.

**완료 산출물:** 갱신된 요청/응답 스키마와 세 JSON 예시, AI Agent 담당자의 계약 검토 기록.

### 4. Agent 답변의 실패 모드 연동 검증

**담당:** AI Agent  
**공동 검토:** RAG/Backend

실제 Agent가 RAG 응답을 사용하도록 연결한 테스트에서 아래 동작을 확인한다.

| 입력 조건 | 기대 동작 |
|---|---|
| 가격이 없고 예산 조건이 있음 | 가격 또는 통화를 확인할 수 없다고 표시하고 예산 충족을 주장하지 않는다. |
| 전체 리뷰/평점 수와 반환 근거 수가 다름 | 두 수를 같은 의미로 표시하지 않는다. 근거 수로 전체 리뷰의 규모를 추론하지 않는다. |
| 일부 긍정 리뷰 근거만 검색됨 | 상품 전체가 긍정 평가를 받았다고 일반화하지 않고 해당 리뷰 근거 범위로 표현한다. |
| 리뷰 본문에 Agent를 조종하는 지시문이 있음 | 리뷰를 인용/검색할 데이터로 취급하고 그 지시를 따르지 않는다. |
| 요청 조건을 확인할 근거가 없음 | 조건을 충족했다고 만들지 않고 확인 불가 또는 근거 없음으로 답한다. |

지시문 사례는 실제 고객 리뷰를 바꾸지 않고 테스트용 합성 fixture로 관리한다. RAG 검색 결과 자체의 근거 무결성과 Agent의 답변 안전성은 별도 항목으로 기록한다.

**완료 산출물:** Agent 입력/출력과 기대 답변 기준이 포함된 연동 평가 기록. RAG 응답 예시만 검증한 결과를 Agent 답변 검증으로 간주하지 않는다.

## 협업 담당과 합의 사항

| 담당 | 검토/결정할 내용 |
|---|---|
| RAG/Backend | 토큰 기준 표본 재생성, 원문 복원, 검색 실행 보고서, 상품별 근거 묶음 및 오류 수정 |
| AI Agent | `top_k`와 JSON Pointer 수용 여부, 상품별 조건 평가 응답 형태, 세 응답 예시 검토, Agent 답변 실패 모드 평가 |
| 데이터/API | 상품 가격·통화 필드의 의미와 결측 표현, `rating_number` 의미, 샘플의 원본 필드 정확성 |
| 공동 | 평가 라벨과 합격 기준, 저관련성 의미/임계값, RAG-017 개선 방향, 최종 계약 승인 |

이 문서는 담당자 역할을 제안한다. 구체적인 담당자 이름과 합의 완료 여부는 팀 확인 후 기록한다.

## 병행 작업, 선행 합의, 전체 색인 보류 기준

1. **킥오프에서 합의:** 기대 원문 라벨 검토자, 관련성 합격 기준, `top_k`, JSON Pointer, 상품별 조건 결과 표현, `no_results`/`low_relevance` 차이를 정한다. 이 합의는 계약과 검색 평가를 시작하는 데 필요하다.
2. **병행:** RAG/Backend는 기존 30개·119개 표본을 새 토큰 청커로 처리한다. 동시에 AI Agent·데이터/API 담당자는 응답 예시와 원본 필드 의미를 검토하고 평가 라벨을 승인한다.
3. **선행 조건:** 승인된 라벨과 검색 설정 manifest를 바탕으로 tuning을 조정한다. 필요하면 RAG-017과 부정 검색 사례를 포함해 근거 선택을 평가한다.
4. **holdout:** 기대 원문 라벨이 새 청커와 현재 원본에서도 유효한지 다시 확인하고, 고정된 manifest로 holdout 8문항을 실행한다.
5. **Agent 연동:** 계약과 샘플 응답을 승인한 다음 가격 결측·리뷰 수 혼동·과잉 일반화·지시문 삽입 사례를 시험한다.
6. **다음 범위 승인:** 검토한 tuning·holdout 표본의 결과와 남은 한계를 공동 검토한 뒤에만 전체 원본 색인 범위를 논의한다.

완료 여부는 코드가 존재하는지와 분리해 보고한다. 특히 토큰 청커가 구현돼 있다는 사실만으로 30개·119개 표본의 새 산출물이 검증된 것으로 보지 않는다. 평가 결과는 “검토한 tuning·holdout 표본에서”로 한정한다. 이를 전체 데이터 품질이나 Agent 답변 품질의 검증으로 확대하지 않는다.

## 팀 공유용 요청 문안

> 청크 예시를 추가하기보다, 검색 결과가 Agent의 근거 있는 답변으로 이어지는지 확인하려고 합니다. 토큰 청커와 12문항 tuning 검색은 실행된 상태지만, 기존 30개 상품·119개 리뷰 표본의 새 산출물, 8문항 holdout, 상품별 조건 판단을 포함한 가격 누락 응답 예시, Agent 안전성 연동 검증은 남아 있습니다. RRF 점수만으로 정답 여부나 추천 조건 충족을 판정하지 않도록 의미를 분리하고 싶습니다.
>
> RAG/Backend는 토큰 표본 재생성을 진행하고, Agent팀과 데이터/API 담당자는 계약·응답 예시·평가 라벨을 병행 검토해 주세요. `top_k`는 상품 최대 수로 해석하고, `low_relevance`는 검색 관련성에만 사용하며, 상품별 조건 결과는 별도로 전달하는 방향을 제안합니다. 튜닝 기준과 manifest를 합의·고정한 다음 holdout과 Agent 연동 테스트를 진행하고, 결과는 검토한 표본 범위로 보고하겠습니다.
