# 전체 상품 RAG 카탈로그 프로필 설계

**상태:** 방향 승인됨; 상세 설계 리뷰 대기
**기준일:** 2026-10-17

## 문제

RAG DB의 `rag.index_runs`는 전역으로 `active` run 하나만 허용한다. 색인 작업은 선택한 카테고리 일부만 처리해도 완료 시 기존 active run을 모두 `superseded`로 바꾼다. 그래서 이어폰 테스트 색인이 전체 상품 검색 대상이 되어 `test_items` 색인을 검색하지 못하는 상태가 생겼다.

검색 API는 이미 색인 run에서 지원 카테고리를 조회하고, 요청 카테고리가 없으면 해당 run 전체를 검색한다. 그러나 그 run을 고르는 방식이 전역 하나뿐이다. 별도 쇼핑 UI 작업본은 요청 카테고리, 검색 화면, 테스트 배지를 `earphones`/`test_earphones`에 고정하고 있어, API의 데이터 범위를 바꿔도 UI가 전체 카탈로그 검색을 하지 않는다.

## 목표

- 현재 선택한 상품 표본을 검색하면서, 향후 원본 카탈로그에 추가되는 카테고리도 같은 전체 상품 검색 흐름에 포함한다.
- `all_products`와 `test_earphones` 같은 색인 프로필별로 활성 run을 독립 관리한다.
- 카테고리 부분 색인이 `all_products`의 전체 스냅샷을 덮어쓰지 못하게 한다.
- 카테고리 이름을 코드에 열거하지 않고 색인 원본에서 동적으로 읽는다.
- 색인 오류나 없는 프로필 때문에 과거의 이어폰 데이터로 조용히 대체 검색하지 않는다.
- 색인 결과의 상품 ID를 상세·variant·장바구니에 쓰는 쇼핑 DB와 일치시킨다.

## 용어와 데이터 의미

- **프로필 (`profile_name`):** 어떤 검색 용도의 색인 run을 활성으로 제공할지 나타내는 안정적인 이름. 기본 프로필은 `all_products`; 별도 테스트는 `test_earphones` 등으로 분리한다.
- **색인 run:** 하나의 원본 데이터 버전, 카테고리 집합, 임베딩 모델, 청커 버전을 담는 불변 스냅샷.
- **전체 스냅샷:** 색인 실행 시작 시 원본이 보고한 모든 카테고리와 상품·리뷰를 포함한 스냅샷. `all_products`는 현재 선택한 원본에 실제로 존재하는 전체 항목을 뜻한다. 지금 원본이 테스트 표본뿐이라면 프로필 이름이 전체 쇼핑몰 상품 수를 보장하지 않는다.
- **부분/테스트 스냅샷:** 원본의 일부 카테고리나 표본만 선택한 run. 이 run은 명시적인 테스트 프로필에서만 활성화한다.

`all_products`의 정본 입력은 사용자가 선택한 쇼핑 DB의 `products`와 `reviews`다. 현재 검증 소스는 `test_items` 표본이다. 색인 입력 어댑터는 이 DB의 전체 현재 스냅샷을 읽고, 제품 ID·카테고리·리뷰 연결을 그대로 보존해야 한다.

현재 확인된 RAG 데이터는 `5432/toss_rag`의 `test_items` run(180 상품, 4,737 리뷰, 6,741 청크, `beauty` 카테고리)과 이어폰 run(50 상품, 1,000 리뷰)이다. 이 설계를 적용할 때 test_items는 현재 선택된 쇼핑 DB 원본의 초기 전체 상품 스냅샷으로 `all_products`에 연결하고, 이어폰 run은 `test_earphones`로 보존한다. 따라서 최초 검색 가능 카테고리는 `beauty`뿐이다. 다른 카테고리가 같은 정본 상품/리뷰 원본에 들어오면 전체 스냅샷 재색인 후 자동으로 추가된다.

## 제안 설계

### 1. 프로필별 활성 포인터

`rag.index_runs`에 `profile_name`을 저장하고 `rag.index_profiles`를 추가한다. 프로필 행은 현재 활성 `run_id`와 변경 시각을 가진다. `index_runs`의 상태는 run 수명 주기(building/active/superseded/failed)를 기록하고, `index_profiles.active_run_id`는 각 프로필의 검색 대상을 결정한다.

현재의 전역 단일-active 고유 인덱스를 프로필별 단일-active 제약으로 바꾼다. 색인 완료 트랜잭션은 새 run의 프로필만 잠그고, 같은 프로필의 이전 run만 supersede한 뒤 새 run과 포인터를 함께 활성화한다. 다른 프로필의 포인터와 run 상태는 건드리지 않는다. 실패한 run은 포인터를 바꾸지 않는다. 기존 run과 chunk를 삭제하거나 재임베딩하지 않는다.

### 2. 전체 스냅샷과 테스트 색인의 분리

- 색인 CLI/API에 `profile_name`을 전달한다. 기본 실행 프로필은 `all_products`다.
- `all_products` 입력은 현재 선택된 쇼핑 DB의 `products`/`reviews` 전체 스냅샷이어야 한다. 원본 DB의 다른 데이터베이스나 이어폰 전용 fixture를 전체 프로필의 입력으로 사용하지 않는다.
- 카테고리를 지정하지 않은 색인은 원본의 카테고리 스냅샷 전체를 처리한다.
- 부분 카테고리 색인을 `all_products`로 활성화하려고 하면 실행을 거부한다. 특정 카테고리 테스트는 `--profile test_<name>`처럼 분리된 프로필로 실행한다.
- 프로필은 카테고리 목록을 뜻하지 않는다. 새 카테고리 키를 코드 변경 없이 전체 스냅샷에 포함한다.
- 스냅샷 버전과 카테고리별 상품·리뷰 수를 색인 전후 비교하는 현재 보호 동작을 유지한다. 입력이 도중에 바뀌거나 개수가 맞지 않으면 활성 포인터를 유지한다.

### 3. 검색 서비스 기본 프로필

RAG 서비스에 `RAG_DEFAULT_PROFILE=all_products` 설정을 추가한다. `active_run()`은 이 프로필의 포인터를 조회한다. 검색 요청에 카테고리가 생략되면 해당 프로필의 모든 카테고리를 검색한다. 카테고리를 지정한 경우 현재 프로필에서 실제 상품이 색인된 카테고리인지 확인하고 BM25·벡터 검색 양쪽에 필터를 적용한다.

프로필이 없거나 아직 활성 run이 없으면 `index_not_ready`를 반환한다. 과거 전역 active run이나 다른 프로필로 fallback하지 않는다. `/healthz`는 기본 프로필 이름, 데이터 버전, 해당 프로필의 `supported_categories`를 반환한다. v0.2 검색 요청·응답 형식은 유지하고, 프로필 선택은 배포 환경 설정으로 고정한다. 별도 프로필을 점검할 때는 같은 DB를 읽는 별도 API 인스턴스를 다른 `RAG_DEFAULT_PROFILE`로 실행한다.

### 4. 쇼핑 화면의 카테고리 중립화

쇼핑 RAG 화면과 요청 작성에서 `earphones` 기본값, `digital|earphones` 타입 제한, `test_earphones` 전용 배지를 제거한다. 카테고리 선택을 사용하지 않는 검색은 `category`를 생략해 전체 상품 프로필을 검색한다. 카테고리 선택을 제공한다면 `/healthz` 또는 서버가 중계한 색인 메타데이터의 `supported_categories`에서 옵션을 채운다. 상품 배지는 실제 결과의 카테고리/데이터 버전을 사용한다.

RAG 실패·미지원 카테고리·상품 ID hydration 실패 시 일반 상품 목록을 추천 결과처럼 대신 보여주지 않는다. RAG가 반환한 `product_id`가 상세·variant·장바구니를 제공하는 동일 쇼핑 DB에 존재하는지 정확히 확인한다. test_items를 검색하면서 상품 DB가 다른 데이터셋이면 해당 상품을 노출하지 말고, 먼저 앱이 같은 test_items 카탈로그를 읽도록 연결하거나 상품 ID가 일치하는 테스트 데이터를 준비한다.

현재 `commerce-storefront` worktree에는 관련 프론트엔드 파일의 미커밋 변경이 있으므로 그 변경을 보존하며 별도 변경 계획에서 수정한다. 이번 설계 작성에서는 해당 worktree 파일을 수정하지 않는다.

### 5. 기존 DB와 서비스의 초기 전환

DB 변경은 새 마이그레이션으로 수행한다. 기존 run, 상품, 청크를 보존하고 전역 active 제약을 프로필 단위로 바꾼다. 기존 이어폰 active run은 `test_earphones` 프로필에, 확인된 test_items run은 `all_products` 프로필에 명시적으로 매핑한다. 프로필 포인터와 run 상태 변경은 한 트랜잭션에서 실행한다.

RAG 서비스는 기존 대상인 `5432/toss_rag`를 계속 사용하되 `RAG_DEFAULT_PROFILE=all_products`로 실행한다. 별도 `15437/toss_rag` Commerce 데모 DB를 자동으로 합치거나 활성화하지 않는다. 서비스 재시작 전후 `/healthz`에서 `all_products`와 `beauty`를 확인한다. 쇼핑 앱 DB는 RAG 결과 ID와 일치하는 데이터 원본을 사용해야 한다.

## 외부 인터페이스와 호환성

- 검색 API 경로와 v0.2 응답 구조는 유지한다.
- `supported_categories`는 선택된 프로필의 활성 run에서 실제 상품이 있는 카테고리만 포함한다.
- 미지원 카테고리는 검색을 다른 카테고리로 넓히지 않고 기존처럼 422 `unsupported_category`를 반환한다.
- `/healthz`에 프로필 이름을 추가한다. 기존 health 필드 이름과 값의 의미는 유지한다.
- UI 변경은 API 계약 승인 또는 RAG API 경로 변경을 요구하지 않으며, 별도 `test_earphones` UI 데모는 운영 전체 상품 검색과 구분해 유지할 수 있다.

## 완료 기준

1. `test_earphones` run을 활성화하거나 재색인해도 `all_products` 포인터와 검색 결과가 바뀌지 않는다.
2. `test_items` run이 `all_products`의 초기 run으로 검색되고, 초기 `supported_categories`가 `beauty`로 표시된다.
3. 전체 스냅샷에 새 카테고리를 추가해 재색인하면 그 카테고리가 별도 코드 변경 없이 `supported_categories`와 검색 결과에 나타난다.
4. 새 전체 run이 실패하거나 완성 전이면 기존 `all_products` 포인터를 유지한다.
5. `all_products` 실행에서 일부 카테고리만 지정하면 run 활성화를 거부하고, 테스트 프로필은 독립 활성화할 수 있다.
6. API 기본 설정이 `all_products`를 가리키며 프로필이 없을 때 이어폰 등 다른 프로필로 fallback하지 않는다.
7. 쇼핑 UI의 검색 요청이 이어폰 카테고리를 자동 추가하지 않으며, 결과 상품 ID가 상세/variant/장바구니 DB에서 정확히 hydrate된다.
8. DB 5432의 기존 run과 데이터가 보존되고 `15437/toss_rag` 및 `main`에는 변경이 없다.

## 범위 밖

- 지금 데이터에 없는 상품 카테고리의 합성/추정 생성.
- 카테고리별 속성 스키마, 속성 추출, 가격·재고 실시간 동기화.
- 임베딩 모델·청킹 규칙·검색 랭킹 변경.
- 쇼핑 DB의 원본 테이블 스키마 변경. 단, RAG 입력 어댑터가 동일한 상품 ID와 카테고리 키를 내야 한다.
- `main` 병합, 원격 push, 배포.
